**Decisions of 2026-10-21 (Linux staging host first; they replace the earlier text wherever it differs, and `docs/cutover/stage-linux.md` is the detailed reference):**
1. **Operator access is an SSH tunnel to a loopback-only listener** (`127.0.0.1:8443`, same host name and certificate). The public `AICC_OPERATOR_CIDRS` allowlist is gone (it stays an optional, empty rehearsal extra; the preflight refuses it on stage/production). Precondition 19 below is superseded.
2. **Certificate method = Option B, Caddy's automatic HTTPS** (Let's Encrypt, HTTP-01/TLS-ALPN-01, no DNS API token). Option A (pre-issued files) and the DNS-01 discussion in precondition 10 are history, kept for reference. The first start uses the Let's Encrypt staging directory.
3. **Caddy talks to PHP-FPM through a unix socket** (`php_fastcgi unix//run/php/aicc-cp.sock`, docroot `/srv/aicc/cp/current` on the Linux hosts (the release tree IS the WordPress root; `edge.env` sets `AICC_WP_ROOT=/srv/aicc/cp/current`), PHP-FPM pool user `aicc-cp`); no HTTP upstream port exists. PHP sees the real client address (`REMOTE_ADDR`) and `HTTPS=on` from Caddy, so `AICC_LM_TRUSTED_PROXIES` stays empty and the `X-Forwarded-Proto` line in `wp-config.php` is not needed (preconditions 1 and the `trusted_proxies` text there are superseded for the Linux hosts).
4. **HTTP/3 is off** (`servers { protocols h1 h2 }`): no UDP 443, no `Alt-Svc`. **Metrics** are enabled on the loopback admin API only and never routed.
5. **The first Linux host is `stage.copilt.org`**, rendered with `node scripts/ops/render-edge.mjs --mode stage`. The production render exists and is tested but **not activated** (the preflight refuses it without `AICC_ALLOW_PRODUCTION_MODE=1`).
6. **Rollback policy after the commercial launch: roll back by redeploying the previous known-good release on the new infrastructure.** GitHub Pages is **only a disaster fallback BEFORE the first customer** (section 5 keeps the DNS-revert procedure for exactly that window).
7. **Test tooling is fail-closed**: `staging:replay`, the browser runner and `rcurl` refuse (exit 3, nothing sent) without an explicit staging host, IP, port and stage id, never talk to production names (except the GET/HEAD-only `--production-readonly`), verify the stage identity before any state-changing request and never follow a redirect off the staging host. Wherever this document says `curl --resolve www.copilt.org:...` for a check, use `scripts/rehearsal/rcurl` with the guard flags instead.

## 5. Rollback

**Policy (owner decision 2026-10-21).** **Before the first customer exists:** the DNS revert to GitHub Pages described below is the disaster fallback (it works only until the Pages certificate in force expires, limit 1 below). **After the commercial launch:** rollback is **the previous known-good release on the new infrastructure** (section 7: repoint `current` for the static site; the previous Control Plane release and its database backup for WordPress), not Pages: the old site has no accounts, no cart and no checkout, so a DNS revert would drop paying customers' access. From the first customer on, the Pages path is no longer a rollback; keep it only as a last-resort static fallback for the marketing pages.

Rollback conditions (any one, after 15 minutes of attempted repair):
- `www` root unavailable or a redirect loop; TLS invalid on `www` for more than 10 minutes;
- `/my-account/`, login, registration or password reset broken; checkout/cart unavailable (once checkout is meant to be open);
- locale routing broken for a language, or widespread asset 404s (`/_next/`, fonts, brand kit);
- the API host or the plugin's calls to it disturbed.
Not a rollback by itself: Watch demo failing alone (page still works), a single non-critical page 404, caption styling.

**What rollback is, and its limit (corrected twice: findings A3, then architecture review F4/F5).** The old site was never touched, so rollback is a DNS change back to GitHub Pages. Three hard limits:

1. **The Pages certificate.** Once DNS leaves GitHub, **GitHub can no longer renew its Let's Encrypt certificate** (it validates over HTTP from its own servers). The old site is a usable rollback **only until the certificate in force at the moment of the flip expires**: **2027-01-18 12:41:22 GMT** as of 2026-10-20 (GitHub renewed on the morning of 2026-10-20; before that it was 2026-11-19; re-verify with `echo | openssl s_client -connect www.copilt.org:443 -servername www.copilt.org | openssl x509 -noout -dates`, runbook 2.3 and 3.1). **After that date a rollback to Pages would present an expired certificate** (an unbypassable error if HSTS were long). Whether GitHub re-provisions a certificate after DNS returns, and whether it keeps `https_enforced`, is **UNVERIFIED** until the throwaway-hostname rehearsal of 1.9 has been run.
2. **Time.** The old statement "back within about five minutes" was wrong and is withdrawn. Facts (re-verified 2026-10-20): the authoritative TTL of `www` CNAME and apex A is **1799-1800 s**; it is 300 s **only if it was lowered 24 hours or more earlier** (2.5); the SOA minimum is **3601 s**, so a resolver that asked while a name had NO record caches the empty answer for up to an hour, in BOTH directions, which is why the plan edits records in place (CNAME target for `www`, A values for the apex) and never deletes then re-adds; browsers keep `301` responses of the apex and of the new aliases (`/account /login /register /shop /store`) and some keep HTTP/3 hints: the edge shortens `Alt-Svc` to `ma=3600` (was Caddy's 30 days) and HSTS is `max-age=300`, and the old site sends neither. Realistic revert time: the registrar edit takes minutes of human time; most clients are back on the old site within **one TTL (300 s with a lowered TTL, up to 1800 s otherwise) plus resolver and browser caches**, with a long tail; plan for 30 minutes to 1 hour of mixed behaviour, not five minutes.
3. **The Control Plane disappears during a rollback.** GitHub Pages has nothing at `/my-account/`, `/cart/`, `/checkout/`, `/pricing/`, `/wp-json/*` (they are 404 there; rehearsal `11-rollback`). While rolled back: customers cannot sign in or see accounts and licenses; **any order in flight cannot complete** and a customer who paid during the window sees a 404 where the confirmation was (no payment gateway is configured today, so no real payment can be in flight now; this changes the day checkout goes live); **plugins in the field that call `.../wp-json/aicc-license/v1/*` (activate, validate, connect POSTs) get a 404/405 from Pages and fail soft** (the product keeps working, entitlement changes and new activations wait); the entitlement outbox keeps running on the Control Plane host's cron, so nothing is lost, but nothing the Backend should hear from the Control Plane is delivered to a customer-visible state until DNS returns. The data never moved, so there is nothing to restore. **Owner decision that follows (record it before the cutover):** (a) **rollback is only offered before the first real customer or order** (then the consequences above are cosmetic), and after that the failure mode is repair-forward on the edge, with the saved mirror served from the edge itself if the whole site must go dark; or (b) give the plugin traffic its own stable hostname that is not part of this DNS flip (an API-style host such as `licenses.copilt.org` pointing at the Control Plane's own TLS endpoint, configured as the plugin's operator-set endpoint), so a revert of `www` leaves accounts-independent plugin calls working. Plugins have no default host (operators configure `AICC_LICENSE_API_ENDPOINT`), so (b) must be decided BEFORE merchants are told which URL to configure. This plan does not choose.

## 7. Release procedure and rollback (static site and Control Plane; as built and run on the Linux host)

**This section replaces the earlier manual `rsync` / `ln -sfn` procedure** (releases under `/srv/aicc/releases`, `current` at `/srv/aicc/current`). That text described a tree Caddy never serves on the Linux hosts and would have bypassed every control below; it is gone. The reference is `infra/release/README.md`; the tools are in `infra/release/`, the host-side commands are installed as `aicc-activate-release` and `aicc-rollback-release`.

**Layout on the host (separate trees per kind):**
```
/srv/aicc/site/releases/<id>/      static export (+ 50x.html; on the staging host also the identity file)   /srv/aicc/site/{current,previous} -> releases/<id>
/srv/aicc/cp/releases/<id>/        WordPress core + WooCommerce + AICC theme/plugin                          /srv/aicc/cp/{current,previous}   -> releases/<id>
/srv/aicc/shared/                  wp-config.php (root:aicc-cp 0640), uploads  (releases symlink to these)
```
Caddy serves `AICC_STATIC_ROOT=/srv/aicc/site/current` and PHP-FPM executes `/srv/aicc/cp/current` (`resolve_root_symlink`). `<id>` = `UTC build time-8 hex of the tree hash` (e.g. `20261021T101500Z-1a2b3c4d`); each release has a manifest and a `SHA256SUMS`.

**Build (Mac, from an approved commit on a clean checkout, never a dirty tree):** `infra/release/build-site-release.sh --target stage|production` (production: no identity file, no blanket Disallow, no noindex outside the error pages; stage: noindex + identity) and `infra/release/build-cp-release.sh` (pinned WordPress/WooCommerce hashes, `git archive HEAD` of the Control Plane worktree, a dirty tree is refused, secret/fixture scan, reproducible tarball). Before building the site run the repo gates: `npm ci`, `npm run seo:check && npm run test:redirects && npm run test:error-page && npm run launch:check` (fail on fake values, Offer/price JSON-LD, the payment placeholder, `.DS_Store`, pending lines). **Known gap (review H-3): the tooling does not yet refuse a DIRTY site tree for the production target, and the CP build path is the feature worktree; build production releases from a tagged commit.** The owner-supplied `NEXT_PUBLIC_*` values are the ones from `docs/AUTHORITY.md`; record which were set in the release notes.

**Deploy (Mac -> host; staging today):** `infra/release/deploy-release.sh --kind site|cp --artifact ... --stage-host ... --stage-ip ... --stage-id ...` verifies the artifact locally, reads the host identity, (cp) takes `aicc-backup --label pre-release`, rsyncs to `.incoming-<id>` and runs `sudo aicc-activate-release`. There is **no production deploy path yet** (blocker B-3, section 11).

**What `aicc-activate-release` does, in order (first failing step stops with nothing changed):**
1. verify every file against `SHA256SUMS` (no missing, no extra file);
2. **pre-release dump gate (cp only, no bypass):** refuses unless `status.json` shows a successful backup finished < 15 minutes ago whose dump exists, matches its sha256 and whose restore check did not fail;
3. **carry-forward (site only):** the `_next/static` chunks that each of the previous 3 releases introduced are copied into the new tree, so a browser holding the previous HTML (an open tab, a cached page) still finds its scripts after the swap (the hashed names never collide). HTML and every other asset come from the new build only. A chunk is carried for exactly 3 further releases. **Limit:** it carries FORWARD only; after a rollback to release R-1, a tab loaded from R requests R-only chunks that R-1 does not contain and gets a 404 (a reload fixes it);
4. root-owned, read-only release tree, then the **atomic swap** (`previous := old current`, `current := new`, each `ln -sfn` + `mv -T` rename; readers see the old or the new tree, never none);
5. cp: graceful PHP-FPM reload (`opcache.validate_timestamps=0` makes it mandatory: new code is picked up only by that reload);
6. **health gate**: the smoke command must succeed twice in a row within 30 s (`smoke-cp.sh`: one FastCGI GET of `/?rest_route=/` against the new real path; `smoke-site.sh`: the required pages, the stage identity and a probe through the running edge). On failure: automatic rollback (`current`/`previous` restored, reload, gate again); exit 3 = rolled back, 4 = the rollback target is also unhealthy (critical);
7. **OPcache warm-up (cp only, after the gate, never fails the release):** `warm-cp.sh` requests `/pricing/`, `/my-account/`, `/cart/` and `/?rest_route=/aicc-license/v1/plans` once through Caddy's public listener on loopback (`curl --resolve <AICC_PUBLIC_HOST>:443:127.0.0.1`, a few seconds each, 30 s budget, user agent `aicc-release-warmup/1`). Reason: the reload empties the 128 MiB OPcache and the review measured 4.8 s for the first `/pricing/` request, 5.3 s for `admin-ajax` and once 11.5 s for a REST request on this host. (`/` is static and the public REST index is a 404, so neither is a useful target.) The same warm-up runs after a healthy manual rollback;
8. prune: the newest 4 releases stay, never `current`/`previous`.

**Rollback:**
* **Static site:** `sudo aicc-rollback-release --kind site` (seconds, no build, no DNS; health-gated; refuses a release marked FAILED). Independent of WordPress.
* **Control Plane, code only:** `sudo aicc-rollback-release --kind cp` (swap, PHP-FPM reload, health gate, warm-up).
* **Code rollback is NOT a database rollback.** Releases must follow the migration rules in `infra/release/README.md` (additive only; expand/migrate/contract over two releases; WooCommerce and WordPress core upgrades are releases like any other and run non-reversible DB updates). If a failed release changed the schema incompatibly, the only remedy is restoring the pre-release dump (`infra/backup/README-backup.md`), which **loses everything written after the dump**. That loss was acceptable before the first order. **After the first order it is not**: a payment gateway may already have captured money for an order the restore erases. Before the first customer, an order-reconciliation procedure for a restore (who decides code-only vs restore, how captured payments are matched) must exist; it does not yet (section 11). Binary logging is currently off (`disable_log_bin`), so there is no point-in-time recovery.
* **Rollback policy after the commercial launch (owner decision 2026-10-21): the previous known-good release on this infrastructure** (the two commands above, plus the pre-release dump for the DB-changing case). GitHub Pages is **only a disaster fallback BEFORE the first customer** (section 5): after the first customer a DNS revert would drop paying customers' access to accounts, cart and checkout.
* Releases are only as reversible as they were tested: the 2026-10-21 staging rollback test swapped two releases with identical content, so it proved the mechanics (symlink, reload, gate) and not that old code returns on this stack with distinguishable code (review H-3). Do one real drill with a one-line marker per release before relying on it.

The admin API itself stays unauthenticated on loopback TCP (residual risk for any other local code).
* **M2 lost-password enumeration.** `POST /my-account/lost-password/` now answers identically for known, unknown and throttled identifiers (the same 302 and the same neutral notice, translated he/es/ru as DRAFTS), sends no mail for an unknown account, throttles 3 per account and 10 per client per hour (IPv6 per /64) invisibly. **Residual:** WooCommerce's registration form still says an account already exists for an address (it must, so a returning customer can sign in); the login form was already generic.
* **L1 cookies** `wordpress_*` / `wp-settings-*` / `wp-postpass_*` carry `SameSite=Lax` (rewritten just before the headers are sent). **L3 CORS**: only the site's own https origin (cleartext only for local development). **L4**: dependency manifests, translation sources, sample data, tests/docs directories are 404 at the edge; default sample content is a gate WARN. **L5**: every target address is parsed (leading zeros, hex/decimal, IPv4-mapped/NAT64/6to4/Teredo, GitHub Pages IPv6) in the Node guard and in all five Mac-side shell tools. **L6**: the REST, login and lost-password counters are atomic, IPv6 is bucketed by /64, 429 carries `Retry-After`. **I1**: whole header families (`X-Forwarded-*`, `X-Remote-*`, `X-Client-*`, `X-Real-*`, `X-Original-*`, `X-Rewrite-*`, `X-Custom-IP-*`, method overrides) are stripped from the FastCGI request. **I2**: AICC Ops parses the Host authority strictly. **L8**: `harden-stage3.sh` (SSH crypto allow-list, unused services; port-22 narrowing is an owner decision).
* **Not addressed here (still open from the review):** L2 raw `file_get_contents` to the metadata address (closed for PHP by the IP filter once deployed; `allow_url_fopen=Off` was not changed), L7 enforcing CSP on WordPress responses, I3 the anonymous `wc-admin` 500 and the missing PHP error log, I4 state-changing GETs of WooCommerce core, off-host encrypted backups (B-2).


## 13. Security review B items that touch the edge, the jails and the API host (2026-10-23)

* **F-09 (`caddy-4xx-flood`)**: a page on any site could make a visitor's browser fire 60 hidden requests (`<img src="https://www.copilt.org/x-N">`) and get the visitor (and their NAT) banned. The filter now counts only 400/401/403/404/405, ignores GET/HEAD for static assets (`/_next/static/`, `/demo/`, image/css/js/font/media/pdf/txt/xml extensions), ignores any request the BROWSER labels `Sec-Fetch-Site: cross-site` (the edge logs that header as `req_sec_fetch_site`; a web page cannot forge or remove it), and the jail threshold is 100 per 60 s. Not a security boundary: a scanner that sends the header escapes the jail; the edge's own deny rules are the boundary. `aicc-wp-login` (POST counters) is documented separately; the sentinel only produces 200s. Tests: `infra/stack-tests/test_fail2ban_regex.py` (explicit expectations + a ground-truth model over ~16,000 real log lines and ~2,600 synthetic ones). Verify on the host after install: `sudo fail2ban-regex /var/log/aicc-edge/aicc-edge.log /etc/fail2ban/filter.d/caddy-4xx-flood.conf`.
* **F-11 (Apache-only protections)**: under Caddy `.htaccess` does nothing. Both listeners now answer the branded 404, whether or not a file exists, for: any dot path segment except `/.well-known/` (`.env`, `.git/...`, `.htaccess`, `.DS_Store`); WooCommerce's `uploads/woocommerce_uploads` and `uploads/wc-logs` and the usual backup/log/upgrade directories (`ai1wm-backups`, `updraft`, `backups`, `wflogs`, `upgrade`, `wc-logs`); and sensitive extensions anywhere (`sql dump bak old orig swp log gz tgz tar zip 7z rar bz2 xz env ini cnf conf yml yaml toml sh pem key p12 pfx sqlite db wpress`). Archives are never public files here: the Plugin ZIP is delivered by a PHP route from a store outside every web root. Proof with a REAL Caddy 2.11.7 (private rehearsal instance, files with a marker in the static root): `~/Downloads/AICC-launch-evidence/infra/f11-real-caddy-proof.txt` (before: 200 for `.env`, `.git/config`, `backup.sql`, `site.zip`, `.hidden`; after: 404; `/.well-known/` still 200). The real run also found that Caddy's regexp engine is RE2 (no look-ahead): the exception for `/.well-known/` is a separate `not path_regexp`, and `test-redirects.mjs` now refuses look-around in any matcher regexp. `production-edge-check.sh` asserts the new paths are not served.
* **F-16 (the API host, documentation only; we do not touch it)**: on `api.copilt.org` the interactive documentation and schema (`/docs`, `/redoc`, `/openapi.json`) answer 200 today. The Backend runbook (G3/B11) already plans `respond 404` for them in the API host's own Caddyfile (`handle /docs* /redoc* /openapi.json { respond 404 }` before the reverse proxy). That Caddyfile lives only on the API Droplet, which this task must not change, so the item is OPEN on the API host: verify after the next planned API change with `curl -s -o /dev/null -w '%{http_code}' https://api.copilt.org/docs` (must be 404; `/health` must stay 200).
