# www.copilt.org cutover runbook and rollback

Status: **PREPARATION ONLY. Nothing here has been executed against production or public DNS.** The edge itself was rehearsed on 2026-10-20 on loopback with a real Caddy 2.11.7 and a disposable WordPress/WooCommerce Control Plane: `docs/cutover/rehearsal.md` (what was proven, what was not, and every change it forced on the template). Every step marked **[OWNER]** needs the owner's explicit approval *at that moment*; approval of this document is not approval of any step, and each irreversible step has its own gate.
Written 2026-10-19 from fresh inspection (DNS, GitHub, headers), the repository audit in `docs/cutover/redirect-matrix.md` and `~/Downloads/AICC-cutover-evidence/`, and revised after the independent review in `~/Downloads/AICC-cutover-evidence/reviewer-A.md` (findings A1-A13 are referenced below).
**Precedence:** where the Control Plane design docs (`docs/unified-experience/domain-migration.md`, `site-architecture.md`) differ from this runbook, **this runbook wins.**

Owner decisions this runbook assumes (fixed): canonical public host `https://www.copilt.org/`; `https://copilt.org/*` 301s to it; `api.copilt.org` stays API-only; the approved Watch demo master is served at `/demo/aicc-demo.mp4`; no payment provider is configured by this plan; **no purchasable-price structured data (schema.org Offer / AggregateOffer / `offers` / price / priceCurrency) is published until real public checkout is live** (switch below); the QA checkout's "Direct bank transfer" is a staging-only placeholder and checkout is not public until a real gateway is configured (precondition 17); the 5xx page is the one-sentence standalone page `docs/cutover/50x.html`.

## 1. Preconditions (all must be true before step 3)

Technical
1. A production WordPress/WooCommerce Control Plane host exists, reachable only through the edge for public traffic, with `home` and `siteurl` set to `https://www.copilt.org`, PHP seeing `https` behind the proxy (`X-Forwarded-Proto`) and the **real client address** (below). **[OWNER]** (separate ops stage; not part of this task).
   wp-config.php on that host (all three are required; the first is the template's WordPress prerequisite, the second is finding A2, the third finding A9):
   ```php
   if ( ( $_SERVER['HTTP_X_FORWARDED_PROTO'] ?? '' ) === 'https' ) { $_SERVER['HTTPS'] = 'on'; }
   define( 'AICC_LM_TRUSTED_PROXIES', array( '<the edge host private IP or CIDR>' ) ); // only X-Forwarded-For from these peers is believed; empty = REMOTE_ADDR
   define( 'DISABLE_WP_CRON', true );                                                  // see 1.3
   ```
   The upstream port must be reachable **only from the edge** (firewall / private interface): the Control Plane believes `X-Forwarded-For` from any peer in `AICC_LM_TRUSTED_PROXIES` (rehearsal VERIFIED: a direct request from the edge's address with a forged XFF is believed).
   The edge overwrites `X-Forwarded-For` (`header_up X-Forwarded-For {remote_host}` in the template; no client-supplied value is passed through and `trusted_proxies` is NOT configured on the public edge). Without `AICC_LM_TRUSTED_PROXIES`, every per-IP rate limit in the license manager (REST 30 requests / 60 s, Connect AICC store options / poll / acknowledge) is one global limit shared by all merchants.
2. A host for the edge (recommended: **Caddy**) with the static `out/` build and the WordPress upstream behind it. **Placement is an [OWNER] decision and has a hard constraint: two Caddy processes cannot both listen on :80/:443 of the same IP address.** The API's Caddy already owns them on 139.59.157.231 (one IPv4 address, ports 80/443 open). So the edge needs (a) its own host, or (b) its own reserved IP address on a shared host (then `bind <that-ip>` in every site block of BOTH Caddyfiles and the API's Caddy must stop listening on the wildcard address, which touches the API host), or (c) the www/apex blocks added to the API's Caddy, which puts the website and the API in one process and one reload domain (the earlier review rejected that as a trust-boundary change, and this plan does not ask for it). Whatever is chosen, the edge runs as its own service with its own user, config directory, state directory and admin port (`docs/cutover/caddy-edge.service.template`: service `aicc-edge`, user `aicc-edge`, `/etc/aicc-edge/`, `/var/lib/aicc-edge/`, `/var/log/aicc-edge/`, admin API `127.0.0.1:12019`, never Caddy's default `localhost:2019` and never the distro `caddy.service`); following the unit literally ON the API droplet would be wrong (UNVERIFIED on Linux, the bind collision could not be reproduced on macOS). Nothing in this plan changes the API host. Reachability: Reachability: **ports 80 and 443 over TCP, and UDP 443 (HTTP/3), on IPv4 and IPv6** from the public internet to the edge (port 80 is needed by HTTP-01 and by the http-to-https redirect); the upstream reachable from the edge on its private address only.

10. **Certificate plan decided** (finding A4, architecture review F1/F13), one of two, and a certificate must never be first tested by the production flip:
    - (i) **Option A, pre-issue before the flip.** Obtain ONE certificate whose SANs cover both `www.copilt.org` and `copilt.org` with DNS-01 and load it with `tls /etc/aicc-edge/certs/fullchain.pem /etc/aicc-edge/certs/privkey.pem` in the template's `(aicc_tls)` snippet. The automated alternative (Caddy or `acme.sh` doing DNS-01 through the DNS provider's API) needs a DNS-provider API token held by the owner and a Caddy build with the provider module; **that is an owner decision this plan does not make and never requests a token for**, and Namecheap's API rewrites whole host-record sets, so a mistake could damage MX/SPF. Adding `_acme-challenge` TXT rows is itself a DNS edit **[OWNER]**, added beside the SPF TXT and removed afterwards.
    - (ii) **Option B, staged start.** Do not give Caddy the real names until DNS points at it. The rehearsed safe waiting state is `auto_https disable_certs` in the global options (https answers a TLS alert, http answers one 301, no loop), but note that `auto_https` takes ONE argument: adding it next to `auto_https disable_redirects` silently replaces that line, so write the staged variant as a separate file and swap it. When DNS has moved, remove it and `systemctl reload aicc-edge` at once. The apex name must stay out of the config until 3.3c (asking for a certificate for a name that still points at GitHub burns failed validations; Let's Encrypt limits failed validations to 5 per hostname per hour). Expected gap: seconds when validation works; if it fails, both names have no TLS until fixed or rolled back. The runbook's smoke test 3.2 cannot run over HTTPS against the production config in this variant (no certificate yet); run it with the rehearsal-style `tls internal` rendering on the same host first.

Do NOT rely on e-mail from the CA: whether the CA still sends expiry notices is not verified here, and the `AICC_ACME_EMAIL` setting is only the ACME account contact. (2) Option A renewal procedure: issue the new pair, copy it over the old files (key 0600, directory 0700, owner `aicc-edge`), run `systemctl reload aicc-edge` (Caddy does not watch certificate files; the unit's `ExecReload` runs the preflight first, which refuses a corrupt, expired, wrong-SAN or mismatched pair so that a bad renewal cannot take a running edge down), then confirm with `cert-expiry-check.sh`. After the flip is stable, empty `(aicc_tls)` and reload to hand renewal to Caddy (HTTP-01, no human), unless the owner prefers to stay manual. (3) Back up Caddy's storage (the ACME account key, issued certificates and keys) off the host, nightly and after every issuance: `scripts/ops/caddy-storage-backup.sh backup /var/lib/aicc-edge/caddy <dir-off-host> [--passphrase-file F]`; restore with `... restore <archive> /var/lib/aicc-edge/caddy` after `systemctl stop aicc-edge` (rehearsal: a Caddy started on restored storage presented the identical certificate, nothing re-issued). (4) The exact owner command sequence and tradeoffs: `docs/cutover/rehearsal.md` section 10; public-CA issuance, DNS-01 and renewal are UNPROVEN (only the internal-CA path and the manual-file form were run).

## 5. Rollback

Rollback conditions (any one, after 15 minutes of attempted repair):
- `www` root unavailable or a redirect loop; TLS invalid on `www` for more than 10 minutes;
- `/my-account/`, login, registration or password reset broken; checkout/cart unavailable (once checkout is meant to be open);
- locale routing broken for a language, or widespread asset 404s (`/_next/`, fonts, brand kit);
- the API host or the plugin's calls to it disturbed.
Not a rollback by itself: Watch demo failing alone (page still works), a single non-critical page 404, caption styling.

**What rollback is, and its limit (corrected twice: findings A3, then architecture review F4/F5).** The old site was never touched, so rollback is a DNS change back to GitHub Pages. Three hard limits:

1. **The Pages certificate.** Once DNS leaves GitHub, **GitHub can no longer renew its Let's Encrypt certificate** (it validates over HTTP from its own servers). The old site is a usable rollback **only until the certificate in force at the moment of the flip expires**: **2027-01-18 12:41:22 GMT** as of 2026-10-20 (GitHub renewed on the morning of 2026-10-20; before that it was 2026-11-19; re-verify with `echo | openssl s_client -connect www.copilt.org:443 -servername www.copilt.org | openssl x509 -noout -dates`, runbook 2.3 and 3.1). **After that date a rollback to Pages would present an expired certificate** (an unbypassable error if HSTS were long). Whether GitHub re-provisions a certificate after DNS returns, and whether it keeps `https_enforced`, is **UNVERIFIED** until the throwaway-hostname rehearsal of 1.9 has been run.
2. **Time.** The old statement "back within about five minutes" was wrong and is withdrawn. Facts (re-verified 2026-10-20): the authoritative TTL of `www` CNAME and apex A is **1799-1800 s**; it is 300 s **only if it was lowered 24 hours or more earlier** (2.5); the SOA minimum is **3601 s**, so a resolver that asked while a name had NO record caches the empty answer for up to an hour, in BOTH directions, which is why the plan edits records in place (CNAME target for `www`, A values for the apex) and never deletes then re-adds; browsers keep `301` responses of the apex and of the new aliases (`/account /login /register /shop /store`) and some keep HTTP/3 hints: the edge shortens `Alt-Svc` to `ma=3600` (was Caddy's 30 days) and HSTS is `max-age=300`, and the old site sends neither. Realistic revert time: the registrar edit takes minutes of human time; most clients are back on the old site within **one TTL (300 s with a lowered TTL, up to 1800 s otherwise) plus resolver and browser caches**, with a long tail; plan for 30 minutes to 1 hour of mixed behaviour, not five minutes.
3. **The Control Plane disappears during a rollback.** GitHub Pages has nothing at `/my-account/`, `/cart/`, `/checkout/`, `/pricing/`, `/wp-json/*` (they are 404 there; rehearsal `11-rollback`). While rolled back: customers cannot sign in or see accounts and licenses; **any order in flight cannot complete** and a customer who paid during the window sees a 404 where the confirmation was (no payment gateway is configured today, so no real payment can be in flight now; this changes the day checkout goes live); **plugins in the field that call `.../wp-json/aicc-license/v1/*` (activate, validate, connect POSTs) get a 404/405 from Pages and fail soft** (the product keeps working, entitlement changes and new activations wait); the entitlement outbox keeps running on the Control Plane host's cron, so nothing is lost, but nothing the Backend should hear from the Control Plane is delivered to a customer-visible state until DNS returns. The data never moved, so there is nothing to restore. **Owner decision that follows (record it before the cutover):** (a) **rollback is only offered before the first real customer or order** (then the consequences above are cosmetic), and after that the failure mode is repair-forward on the edge, with the saved mirror served from the edge itself if the whole site must go dark; or (b) give the plugin traffic its own stable hostname that is not part of this DNS flip (an API-style host such as `licenses.copilt.org` pointing at the Control Plane's own TLS endpoint, configured as the plugin's operator-set endpoint), so a revert of `www` leaves accounts-independent plugin calls working. Plugins have no default host (operators configure `AICC_LICENSE_API_ENDPOINT`), so (b) must be decided BEFORE merchants are told which URL to configure. This plan does not choose.

1. Namecheap: restore the saved values **by editing, not deleting**: the `www` CNAME target back to `avivg7.github.io.`; the apex A records back to the four GitHub addresses `185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153` (edit each; remove an extra edge address last). ## 7. Static release procedure and rollback (finding A12)

The static site is served from a versioned directory behind an atomic symlink; nothing else deploys it (the Pages deploy job is gone).

Layout on the edge host: `/srv/aicc/releases/<UTC timestamp>-<short sha>/` (one directory per release, containing the contents of `out/` **plus `50x.html`** copied from `docs/cutover/50x.html`, **plus the `_next/static` files introduced by the previous 3 releases**, see below), `/srv/aicc/current` -> the active release, and Caddy's `AICC_STATIC_ROOT=/srv/aicc/current`. The edge's preflight refuses a release without `index.html`, `404.html` and `50x.html`.

**Why the previous releases' chunks are carried (architecture review F7, reproduced):** the symlink swap is atomic and lossless (0 failures in 42,527 requests during a swap), but the new release used to contain only ITS OWN hashed `_next/static/*` files, so a browser holding the previous release's HTML (an open tab, a cached page, a `next/link` prefetch) got `404` for every script and stylesheet the moment the swap happened, and `/_next/static/*` is cached `immutable` for a year, so mixed states are common. Hashed names never collide, so a release now ALSO contains the `_next/static` files that each of the previous 3 releases introduced (each release records only its OWN files in `<release>.static.txt`, so a chunk is carried for exactly 3 further releases and then dropped); HTML and every other asset come from the new build only. Release directories beyond the newest 4 (the new one plus 3) are pruned. `node scripts/rehearsal/rehearsal.mjs release` does exactly this; on the edge host use the same steps (below). Rehearsed (`16-release-swap`): the old HTML's chunk answers 200 after a swap, two live swaps under a 6-worker probe lost zero requests, the 4th release dropped the 1st release's chunk (404, not 5xx). Not tested: how Next.js reacts on a chunk 404 beyond the window (a tab older than three releases still needs a reload).

Build from an approved commit, on a clean checkout, never from a dirty working tree:
```
git fetch && git checkout <approved sha> && git status --porcelain   # must be empty
npm ci
AICC_BASE_PATH="" SITE_URL=https://www.copilt.org \
  NEXT_PUBLIC_LEGAL_REVIEW_APPROVED=<true only after counsel approval, else unset> \
  NEXT_PUBLIC_AICC_LEGAL_NAME=… NEXT_PUBLIC_AICC_ADDRESS=… NEXT_PUBLIC_AICC_SUPPORT_EMAIL=… \
  NEXT_PUBLIC_AICC_GOVERNING_LAW=… NEXT_PUBLIC_AICC_PAYMENT_PROCESSOR=… NEXT_PUBLIC_AICC_HOSTING_REGION=… \
  npm run build                                  # NEXT_PUBLIC_AICC_ACCOUNT_URL stays unset: the default is https://www.copilt.org/my-account/
npm run seo:check && npm run test:redirects && npm run test:error-page && npm run launch:check   # fails on fake values, Offer/price JSON-LD, the payment placeholder, .DS_Store, pending lines, no payment processor, no /get-started/ route
```

(Node 20; the owner-supplied `NEXT_PUBLIC_*` values are the ones from `docs/AUTHORITY.md`; record which were set in the release notes.)

Deploy **[OWNER for the first one and for any release after the cutover]**:
1. `find out -name .DS_Store -delete` (Finder files must never be published), then `R=/srv/aicc/releases/$(date -u +%Y%m%dT%H%M%SZ)-<sha>; mkdir -p $R && rsync -a --delete --exclude .DS_Store out/ $R/` (record the build's own chunk list: `(cd $R/_next/static && find . -type f | sort) > $R.static.txt`), then for each of the previous 3 releases `P`: `rsync -a --ignore-existing --files-from=$P.static.txt $P/_next/static/ $R/_next/static/`, then `cp docs/cutover/50x.html $R/50x.html && (cd $R && find . -type f -print0 | sort -z | xargs -0 shasum -a 256 > ../$(basename $R).sha256)`; keep the newest 4 release directories (with their `.sha256` and `.static.txt`) and delete older ones.
