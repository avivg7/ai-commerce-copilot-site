## 1. Recommendation: Caddy as the thin edge

The CP docs allow "nginx on the WordPress host, or a CDN with path rules" (`domain-migration.md` A11.4). The repositories contain **no production deployment
config for the static site or for WordPress** (the CP `docker/` folder is a development Apache stack; the only production edge anywhere is the Backend's Caddy
on the DigitalOcean droplet, `aicc-backend/docs/digitalocean-infrastructure.md` section 11, whose Caddyfile lives only on the server). Recommendation: **Caddy**.

* the API host already runs Caddy, so it is the one edge tool the operator already runs and monitors (no new service to learn, no external CDN to approve);
* it obtains and renews certificates for **both** `copilt.org` and `www.copilt.org` by itself (the apex needs a valid certificate or its https redirect fails before it can redirect);
* the whole rule set is a few hundred readable lines; `reverse_proxy` passes `Host`, `Cookie` and `Set-Cookie` untouched, adds `X-Forwarded-Proto`, and does not cache (stock Caddy has no HTTP cache, so there is nothing that can cache a signed-in page);
* nginx would work equally (the rules are edge-agnostic: the data in `redirect-matrix.mjs` is the contract) but adds nothing here; a hosted CDN needs the owner's approval and cannot be rehearsed offline.

Where Caddy runs is an **owner/ops decision**: do not put it in the same Caddyfile/process as the API (the Backend's `TRUST_PROXY_HEADERS=true` is safe *because Caddy is the only proxy in front of it*, `digitalocean-infrastructure.md` section 10). A second small host, or a separate Caddy instance, keeps that assumption and the API's blast radius untouched. DNS would then point `www` and the apex at the edge host; `api` keeps its A record to 139.59.157.231.

## 2. Host and scheme rules (apply to every request on the three non-canonical origins)

| # | Request | Response | Why |
|---|---|---|---|
| H1 | `http://copilt.org/<p>?<q>`, `https://copilt.org/<p>?<q>`, `http://www.copilt.org/<p>?<q>` | `301` (GET, HEAD) or `308` (any other method) to `https://www.copilt.org/<p>?<q>` | one canonical host, **one hop** from every variant (no http -> https -> www chain); 308 keeps the method of a POST that reaches the apex (see the plugin note in section 9) |
| H2 | `https://www.copilt.org/...` | no host redirect | canonical |
| H3 | `api.copilt.org` | **not handled by this edge, ever** | separate Caddy site block on the API host; never redirected, never proxied here |
| H4 | any other `Host` | not served (no site block) | |

Path rules in section 3 run **before** H1 and produce absolute `https://www.copilt.org` targets, so `https://copilt.org/account/` goes to `https://www.copilt.org/my-account/` in one hop, not apex-then-alias.

## 3. Path rules (301 for GET/HEAD and 308 for every other method; the query string is always kept, a language prefix is always kept)

Like the host rule, every path rule is a pair: GET/HEAD answer `301`, any other method `308` (reviewer finding A5: a POST to a slash-less `/checkout/order-received/12` or `/account` must keep its method and body; the generated Caddyfile carries four matchers per rule: query/no query x safe/unsafe method). Order matters (first match wins). `cutover-only` = only relevant once this edge serves the host (everything in this file is cutover-only; the extra mark means "also only if the old URL was ever linked or indexed").

| id | From (regex on the path) | To | Notes | Matters |
|---|---|---|---|---|
| `base_index` | `/ai-commerce-copilot-site/<dir>/index.html` | `/<dir>/` | old GitHub Pages sub-path | cutover, only if ever linked/indexed |
| `base_root` | `/ai-commerce-copilot-site` and `/ai-commerce-copilot-site/` | `/` | same | same |
| `base_slash` | `/ai-commerce-copilot-site/<anything>/` | `/<anything>/` | same | same |

What is deliberately **not** redirected:

* **Uppercase variants** (`/Pricing/`, `/PRODUCT/`): not folded. URL paths are case-sensitive, nothing links to them, and the static origin returns a branded 404 (Linux file system). Folding would add 9+ rules for no known inbound link. Caddy's `path` matcher is case-insensitive but `path_regexp` is not; the template uses `path_regexp` throughout so behaviour is deterministic. (On a case-insensitive file system, e.g. a Mac, `file_server` would serve them: do not rehearse case behaviour on macOS.)
* **Locale prefix `/en/`**: English has no prefix (`parseSlug` returns null); `/en/...` is a 404, not a redirect, so there is no second URL for English.
* **Legal and pricing "static copies"** (section 5): same URL, so there is no HTTP redirect at all.
* **`/wp-json/...` and other machine paths**: never given a trailing slash (REST routes are slash-less), never language-prefixed (`/he/wp-json/...` is a 404 by design in `class-aicc-lm-i18n.php`).

## 7. Trailing slash, locale prefix, case: the rules the edge must preserve

* Every public page URL has a **trailing slash** (`trailingSlash: true` in `next.config.ts`; canonical and hreflang end in `/`). A bare page URL gets the slash in a **single 301** (`slash_*` rules), also from the apex. Files with an extension (`/robots.txt`, `/sitemap.xml`, assets) and machine paths (`/wp-json/...`) never get a slash.
* The **language prefix** (`/he/`, `/es/`, `/ru/`) is part of the URL end to end: no rule drops, adds or rewrites it; WordPress strips it itself (`AICC_LM_I18n`). English has no prefix and `/en/` is a 404. The password-reset cookie bug (cookie `Path` derived from a stripped URL) came from exactly this class of rewrite: **the edge must forward `/he/...` unchanged** to WordPress.
* Cross-origin links are language-aware (resolved 2026-10-19): the static site's Get started, Sign in, Account and plan buttons are `getStartedUrl(locale)` / `planUrl(plan, locale)` (`src/lib/site.ts`): `https://www.copilt.org/my-account/` in English, `https://www.copilt.org/he/my-account/` (and `/es/`, `/ru/`) otherwise, `?plan=` kept. The edge needs no rule for them: `/he/my-account/...` is WordPress-owned (rule 8) and forwarded unchanged, and the aliases `alias_account`, `slash_pages`, `slash_wp_deep` keep the prefix. `npm run test:redirects` replays all four languages x Get started and the three plan links through the stand-in edge (200 from WordPress, no redirect), and `npm run test:interaction` checks every account link on every page in every language.
* `index.html` duplicates are redirected (`index_html`); directory URLs are the only form.
* **Uppercase**: not folded (section 3).

## 8. Rehearsal: what was and was not done

Done (offline, `npm run test:redirects`, 2026-10-19, updated for the round-2 review):

1. The Caddyfile template's generated blocks are rebuilt from `redirect-matrix.mjs` and compared byte for byte (drift fails the test; `node scripts/test-redirects.mjs --write` regenerates).
2. The template is parsed into a **model of the whole file**: the generated redirect/routing text (a subset: `path_regexp`, `method`, `not method`, the two `expression` forms, `redir`, `handle`, `import`, `error`, `header Cache-Control`) **and the site blocks** (the apex and www addresses, which snippets each block imports, the HSTS and security headers those snippets add, Caddy's automatic http-to-https redirect for a host with no explicit http block). The model is served on a loopback port and **165 hand-written expectations** are replayed over real HTTP with an explicit `Host` and scheme per request: status, exact `Location`, origin, `Cache-Control`, plus `Strict-Transport-Security: max-age=300` and `nosniff` on every answer.
3. A sweep sends 66 representative paths to each of `http://copilt.org`, `https://copilt.org`, `http://www.copilt.org`, `https://www.copilt.org` and follows redirects: **at most one hop, never a loop, always ends on `https://www.copilt.org`**, and a canonical slashed URL never redirects.
4. Every route in `src/lib/routes.ts` x four languages has exactly one owner, the static-owned ones exist in the build, the WordPress-only pages and the unowned list behave as documented, and the template contains no `includeSubDomains`/`preload`, no `api.copilt.org` site block, and no Cookie/Set-Cookie rewriting.
5. **Mutant self-test** (`node scripts/test-redirects.mjs --self-test`, also run at the end of `npm run test:redirects`): ten scratch mutants of the template must make the harness fail: delete `import aicc_redirects` from www (and from the apex), drop `http://www.copilt.org` from the apex address list, delete `import hsts` from the apex (and from www), delete `import security_headers` from the apex, add `includeSubDomains`, tamper with a generated routing line, turn the host redirect for other methods into a 301, add an `api.copilt.org` block. Before this round the first three of those survived (finding A7).

What this proves, exactly: the generated text is what the matrix says, and a model of the file built from that text (site blocks, imports, matcher order) gives the hand-written results. What it does **not** prove: that real Caddy accepts the file; that Caddy's directive order, `expression`, `path_regexp` capture placeholders (`{re.name.N}`), `handle`/`redir` ordering, `header_down`, `handle_errors` and the log filter behave as modelled (they are modelled from the documentation); anything about TLS, certificates, HTTP/3, IPv6 or the upstreams; and that the 165 expected results are right: their author also wrote the rules, so they are an oracle only as far as a reviewer agrees with them.

**Not done, and not claimed**: no real Caddy or nginx was run (neither is installed; the Docker daemon is not running; nothing was installed or pulled). **Hard gate before cutover** (runbook section 1): `caddy validate --config Caddyfile` on the real binary, then a `curl --resolve www.copilt.org:443:<staging-ip> -I ...` replay of the same case list (including the POST cases, the prefixed `wc-ajax` roots and the Cache-Control expectations) on a staging host with a real WordPress behind it (login, cart, checkout, reset password under `/he/`, a `wp_remote_post` to `/wp-json/aicc-license/v1/activate` on the apex). The case list in `redirect-matrix.mjs` is written so it can be replayed with curl.

## 9. Hidden dependencies the cutover can break (short list; details in `architecture-current-target.md`)

1. **WordPress `home` / `siteurl`** must be `https://www.copilt.org`. The theme's canonical, hreflang, sitemap, robots `Sitemap:` line and every absolute link are built from `get_option('home')`, and `AICC_LM_I18n` only language-prefixes URLs whose host equals `home`. WordPress cookie names embed a hash of `siteurl`: set it right before the first customer, never change it later. If WordPress sits behind this edge over http it must see `X-Forwarded-Proto` (`$_SERVER['HTTPS']='on'`), else `is_ssl()` is false: the `aicc_plan` cookie loses `Secure` and WordPress emits `http://` URLs.
2. **Shipped plugins call the Control Plane with a POST** (`/wp-json/aicc-license/v1/activate`, `connect/ack`, `connect/abandon`). The plugin has *no default host*: operators configure `AICC_LICENSE_API_ENDPOINT` (and `AICC_API_ENDPOINT` for the Backend). A store configured with the apex hits H1. **Corrected (finding A8, read in the installed WordPress 7.1):** WordPress's HTTP API does *not* turn a POST into a GET after a 301, 307 or 308: `WP_Http::browser_redirect_compatibility()` (`wp-includes/class-wp-http.php`, ~514-519) changes the method to GET **only for a 302**, and `Requests::parse_response()` (`wp-includes/Requests/src/Requests.php`, ~787-811) re-sends the same method, headers and body for every other redirect (`Response::is_redirect()` counts 300-303, 307 and every code from 308 to 399); the plugin's POSTs use the default of 5 redirects. So H1's `308` is sufficient (a `301` would have worked for this client too); what *would* break is a **302** anywhere on the path, or a client that does not follow redirects (the Backend's `httpx` does not by default; the Backend does not call the Control Plane in the code reviewed). Rule kept: every documented endpoint value is the `www` host. Browsers and other HTTP clients differ from WordPress (they convert a 301 POST to GET), which is why the path rules now also answer 308 for non-GET (A5). **Staging test required:** a real `wp_remote_post( 'https://copilt.org/wp-json/aicc-license/v1/validate', ... )` with a dummy license key (a harmless, rate-limited POST route) from a WordPress/plugin fixture, resolving the apex to the staging edge, must end with a 200 body from WordPress after exactly one 308 (`$response['http_response']->get_response_object()->history` has one entry).
3. **Plugin and docs still name the wrong hosts**: `PRODUCTION_API_URL = https://aicc-backend-ij4c.onrender.com` (historical constant, not a default), `Plugin URI: https://aicommerce.io`, theme `Theme URI: https://aicommerce.io`, the WordPress.org readme draft links `https://copilt.org/terms/` etc. (apex) and `/get-started/` (not built). Owner/plugin work, not changed here.
4. **Search Console / Bing**: add `https://www.copilt.org/` (or a domain property via DNS TXT) and submit `https://www.copilt.org/sitemap.xml`. The old site's sitemap/og:url point at `aicommercecopilot.com`, an unregistered domain: nothing to migrate, nothing is indexed under copilt.org (UNVERIFIED beyond two web searches).
5. **GitHub Pages**: it currently owns the apex A records and the `www` CNAME and does the apex-to-www 301. The workflow `.github/workflows/nextjs.yml` on this branch is now **build-and-test only** (the Pages deploy job and its `pages: write` permission were removed, finding A12), so a casual merge to `main` can no longer replace the old site; the old `main` HEAD `815350b` is also tagged locally (`old-site-rollback-815350b`, never pushed). Pages keeps serving its last deployed artifact until DNS moves; that artifact is the rollback (runbook section 5, including the certificate limit). Until the edge and WordPress exist, the static site's Get started / Sign in / plan buttons would link to `https://www.copilt.org/my-account/`, which is a 404 on Pages. Removing the Pages custom domain while DNS still points at GitHub makes the host claimable by another account (takeover): move DNS first, then remove the custom domain.
6. **Next client navigation**: links to the five WordPress-owned routes use `next/link` (`LocaleLink`, `SiteHeader`, `Button`, `rich.tsx`), so the static pages prefetch `/<route>/__next*.txt`. Rule 6 answers those with a cheap 404 (never PHP) and Next falls back to a normal page load. Cleaner fix, small and copy-free but outside this task: render links to `MIRROR_ROUTES` as plain `<a>` once the edge is live.
7. **HSTS**: start at `max-age=300` on `www` (and on the apex's https responses), no `includeSubDomains`, no `preload`. `includeSubDomains` on the apex would cover `api.copilt.org` and any staging host; on `www` it would only cover `*.www.copilt.org`. Raise `max-age` after the staging pass.
8. **Cached redirects and TTL**: 301s are cached by browsers; the apex-to-www 301 already exists today (GitHub), so H1 changes nothing for returning visitors. Current DNS TTLs: the registrar's authoritative TTL is **1800 s** (reviewer read 1799-1800 s at `dns1.registrar-servers.com` for apex A, MX, TXT and the `www` CNAME; a recursive resolver showed 1799 s on 2026-10-19; the 817 s seen earlier was a cached remainder). Lower the `www` and apex TTLs to 300 s a day before the DNS move (30 minutes is the minimum that matters), and keep MX/TXT (Namecheap email forwarding, SPF `include:spf.efwd.registrar-servers.com`) exactly as they are. No CAA record exists; if one is added it must allow the edge's CA (Let's Encrypt/ZeroSSL for Caddy).
9. **Sitemap and robots**: both WordPress and the site generate `/sitemap.xml` and `/robots.txt`; the edge serves the **site's** (rule 3). The site's robots now disallows `/my-account/`, `/checkout/`, `/cart/` (with language prefixes) like WordPress's did. The site's sitemap lists 40 URLs: the 36 built pages plus `/data-processing-addendum/` in four languages (`WORDPRESS_SITEMAP_PAGES` in `src/lib/routes.ts` = `WP_SITEMAP_PAGES` in `redirect-matrix.mjs`; the Control Plane publishes the DPA publicly, indexable (no noindex; only account, cart and checkout are noindex), with canonical + hreflang x4, in its own sitemap and in its footer; lastmod stays the single legal-draft date). `npm run seo:check` fails if those four URLs go missing or their hreflang cluster is not the four languages + `x-default`; `npm run test:redirects` fails if the lists differ or the edge sends them anywhere but WordPress. No sitemap index is needed while WordPress has no other indexable page missing here. Note: the static site's own footer still does not link the DPA (only the Control Plane's does); an owner/content question, not a sitemap one.
10. **Mail**: the apex has forwarding MX and an SPF record that authorises only Namecheap's forwarder (`v=spf1 include:spf.efwd.registrar-servers.com ~all`). WooCommerce emails (password reset, order, license) from `@copilt.org` need a sending provider in SPF and a DKIM key, and a provider needs the single SPF record edited (two SPF TXT records are invalid). **This plan does NOT edit SPF/MX/TXT.** OWNER DECISION before any customer email is sent: pick the sender, then change SPF/DKIM as a separate, owner-approved DNS change. No account smoke test that sends mail can be called green before then.
11. **Real client address (finding A2).** Behind the edge PHP sees the edge as `REMOTE_ADDR`; the Control Plane's per-IP rate limits (REST 30 requests / 60 s, Connect AICC store options, poll and acknowledge) would become **one global limit for all merchants**, and any payment gateway that checks the callback source IP would see the edge. The edge overwrites `X-Forwarded-For` with the address Caddy saw (`header_up X-Forwarded-For {remote_host}` in both WordPress snippets; never add `trusted_proxies` to the public edge). The license-manager plugin now has `AICC_LM_Client_IP` (`AICC_LM_TRUSTED_PROXIES` constant, empty by default: no change in QA/development) which believes the header only when `REMOTE_ADDR` is a listed proxy and reads it from the right. wp-config snippet and the two-source-IP smoke test: runbook sections 1 and 4.
12. **WP-Cron (finding A9).** The entitlement outbox delivery to the Backend (every five minutes, `aicc_lm_entitlement_delivery`) and the daily expiry sweep (`aicc_lm_expiry_sweep`) run on WP-Cron, whose default trigger is a loopback HTTP request to `https://www.copilt.org/wp-cron.php`. It silently fails whenever the WordPress host cannot reach the public edge (including all of the rehearsal while DNS still points at GitHub). Production: `DISABLE_WP_CRON` true plus a system cron (`* * * * * wp cron event run --due-now`). Smoke test: runbook section 4.
