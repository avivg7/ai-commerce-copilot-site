## Accepted residual risks (owner decisions, recorded)

* **F-18 (the lead's list calls it F-21) `aicc` has `NOPASSWD:ALL` sudo; the operator SSH key is root.** Model: one operator, one host, key-only SSH, `PermitRootLogin no`, fail2ban, a passphrase-protected operator key in the keychain (`ssh-access.md`), the restricted off-host account is separate (single sudo rule, forced command, root-owned `authorized_keys`). A stolen unlocked operator key is a root compromise of the host; the mitigations are the passphrase, the second key kept offline, DigitalOcean 2FA and the console recovery path. Narrowing sudo (a command allow-list) would break `deploy-release.sh` (`aicc-activate-release`, `aicc-backup`, `rsync` into root-owned trees, `aicc-wp`, `systemctl`) and gains little while the same user owns the release trees. **Accepted for launch. Owner decision: ______ (date, initials).** Revisit when a second operator or CI exists.
* **F-17 registration is bounded per IP only (IPv6 /64 rotation, no per-origin uniqueness).** Application item (Backend); storage growth only in ENFORCED mode. Not an infrastructure control. Open with the Backend owner.
* **F-19 CSP is Report-Only with no collector.** Accepted for launch (`production-promotion.md` section 3): the static export needs `'unsafe-inline'`, WordPress/WooCommerce inline scripts, the payment origins are unknown; Report-Only without an endpoint produces browser-console messages only, so it protects nothing today and is a development aid. Enforcing it (plus `frame-ancestors`/per-gateway rules for checkout and a report collector) is a post-launch item once a gateway and nonces/hashes exist.
* **F-20 `email_hash` salt is the public store id (Plugin).** Application item, owner decision on a site-secret pepper vs cross-order matching after reinstall; not infrastructure.
* **F-21 origin normalisation without IDNA/NFKC.** Application item; test one IDN store before launch.
* **F-22 the off-host `ack` is an assertion by the key holder, not proof of possession.** `aicc-offhost-serve ack` checks the hashes against the host's own sidecars, so a key holder could acknowledge a set it never fetched, and AICC Ops "off-host verified" is therefore an assertion. A server-nonce challenge (the host sends a random value, the puller returns a hash of nonce+file) would close it; not implemented. Acceptable in a single-owner setup because the key holder is the owner. With F-05 the Mac now holds ciphertext, so "verified" additionally means "stored encrypted", which the host cannot see either.
* **F-23 staging tooling uses trust-on-first-use (`StrictHostKeyChecking=accept-new`).** Production paths require a pinned `known_hosts` (deploy, pull, tunnel, publish, push-bundle, drill). The staging path is being retired with the promotion (`production-promotion.md`).
* **F-24 the hourly `aicc-security-updates` run can restart MySQL (package postinst) at a random minute.** Already documented as "never touches MySQL by itself"; dpkg postinst of a `mysql-server` package does restart it. Expect a rare 5-10 s blip (the daily default already had the property); `service_down`/`db_down` alerts need 2 samples (60 s) so a short restart does not page.
* **Stage TOFU ssh** is the same item as F-23.
* **F-06 shared symmetric secrets on the internet-facing WordPress host** (reviewer MEDIUM, Backend/CP design): a PHP code-execution bug in WordPress/plugins would yield both secrets. Infrastructure side: PHP-FPM is sandboxed (IP filter, `ProtectSystem=strict`, no shell functions), `wp-config.php` is `root:aicc-cp 0640`, the secrets are rotated by re-running the promotion/renderer. Asymmetric signing is the proper fix and is not infrastructure work. Rotate both on any Control Plane incident.
* **F-07 plugin self-update single trust root:** `publish-plugin-release.sh` already supports a second hash channel (`--sha256-file`); making it mandatory for production and adding a detached signature are release-process items (owner/Plugin repo).

## Not fixed here (for completeness)

The API host's Caddy (F-16); anything in the Backend, Control Plane or Plugin repositories; the owner-held key material for F-05 (generating and storing the recipient key pair is an owner gate); a real end-to-end `aicc-restore live` of the re-render step on the host (it can only run on the real host: the isolated rehearsal proves the renderer + hash, the text gates prove the step order).
