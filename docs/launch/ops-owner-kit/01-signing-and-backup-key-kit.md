## A. Plugin update-signing keys (primary + standby)

### A1. Create the two encrypted key vaults (10 min)

Plug in STICK-1. In Terminal (you are asked for a passphrase; choose a long one and save it in the password manager under "AICC primary key vault"; do NOT tick "remember in keychain"):
```bash
hdiutil create -size 16m -encryption AES-256 -fs APFS -volname AICCKEYS-PRIMARY "/Volumes/<STICK-1>/aicc-keys-primary.dmg"
hdiutil attach "/Volumes/<STICK-1>/aicc-keys-primary.dmg"        # mounts at /Volumes/AICCKEYS-PRIMARY
```
Same for STICK-2 with `AICCKEYS-STANDBY` / `aicc-keys-standby.dmg` / a different passphrase ("AICC standby key vault").

### A2. Generate the keys straight onto the vaults (3 min)
```bash
PLUG=~/Projects/ai-commerce-copilot-worktrees/release-1.1.0-prep     # the worktree that holds the approved 1.1.0 release commit (until it is landed on launch/integration)
umask 077
php "$PLUG/bin/sign-release.php" keygen --secret-out /Volumes/AICCKEYS-PRIMARY/aicc-release-primary.key
php "$PLUG/bin/sign-release.php" keygen --secret-out /Volumes/AICCKEYS-STANDBY/aicc-release-standby.key
```
Each prints three lines: where the secret key was written (`secret key written to <path> (mode 0600). Keep it OFFLINE ...`), then `public key ...` (44 characters, ends in `=`) and `fingerprint: xxxx-xxxx-xxxx-xxxx`. Write both pairs into a text note for yourself (public values, not secrets). The tool refuses a path inside the repo, a relative path and overwriting an existing key (all proven). The key file is a single base64 line, mode 0600.

### A3. Make the second copy of each secret and verify the fingerprint independently (10 min)

For each key, put the file content into the password manager as a secure note (`pbcopy < FILE`, paste into the note, then `pbcopy < /dev/null` to clear the clipboard). Then check the stored public key and fingerprint WITHOUT any AICC code:
```bash
# public key from the secret file (prints only the public half):
php -r '$s=base64_decode(trim(file_get_contents($argv[1])),true);echo base64_encode(sodium_crypto_sign_publickey_from_secretkey($s)),"\n";' /Volumes/AICCKEYS-PRIMARY/aicc-release-primary.key
# fingerprint recomputed with plain shasum (must equal the one keygen printed):
printf '%s' '<PUBLIC KEY>' | base64 -D | shasum -a 256 | cut -c1-16 | sed -E 's/(....)(....)(....)(....)/\1-\2-\3-\4/'
```
Then `hdiutil detach /Volumes/AICCKEYS-PRIMARY` and `hdiutil detach /Volumes/AICCKEYS-STANDBY`; put STICK-1 and STICK-2 in different places. Losing BOTH the primary and the standby (all copies) means no signed update can ever reach the fleet again (merchants would reinstall from the account page).

### A4. Put the PUBLIC keys in the Plugin repo (2 min, the only thing that goes into git)

File: `release/endpoints.conf` in the Plugin repo (the line `UPDATE_PUBLIC_KEYS=` is empty on the integration head ded0fb4; the 1.1.0 release-preparation branch carries your two PUBLIC keys, primary first).
```
UPDATE_PUBLIC_KEYS=<primary public key>,<standby public key>
```
Primary FIRST. Commit that file (a release is built only from a clean commit). Also before the first release (not part of this kit, Claude can do it on request): the first version is 1.1.0 (chosen by the owner; a `-dev`/`-rc` version must NOT ship, and the production publisher AND `first-signed-release.sh` stage 0 refuse one), bump the Version header, `AICC_VERSION` and the readme Stable tag, add `release/notes/1.1.0.md`.

Where else the public keys go (the Control Plane production wp-config line below is MANDATORY before the release is made current; none of them is secret):
| Place | What | When |
|---|---|---|
| Control Plane production `wp-config.php` | **on the host: `sudo aicc-owner-facts set AICC_LM_PLUGIN_SIGNING_PUBKEYS '<primary>,<standby>'`, then `sudo aicc-render-wp-config --env production --confirm-production` and `sudo systemctl reload php8.3-fpm`** (public keys only, validated: 32-byte Ed25519, at most 2). Do NOT hand-edit the rendered wp-config: the next render erases it. This is the HOST'S TRUST ANCHOR: the keys a ZIP bakes into itself prove nothing about who signed it, so the Control Plane judges every release against this list. A production host serves nothing while it is unset and the launch gate BLOCKS on it (it used to be a note). It must contain a key the shipped build carries. Afterwards run `sudo aicc-owner-facts export > owner-facts.env` and keep that file with your records (the facts file is not in any backup). | before the release is made current (first-signed-release.sh stage 6) |
| The website / README | the two FINGERPRINTS, so merchants can compare them with the one shown on their account page | after step A5; tell Claude the fingerprints |
| A store's `wp-config.php` (`AICC_UPDATE_PUBLIC_KEYS`) | emergency/rotation only | never in normal operation |

### A5. TEST-SIGN with the real tooling, tamper, confirm rejection (10 min)

This is exactly what `scripts/signing-selftest.sh` does with throwaway keys; do it once with your real keys in a SCRATCH worktree (not the integration worktree) so you know the keys work BEFORE launch day. The scratch worktree is a detached checkout of the commit that holds your A4 commit, so the build bakes your keys. The version it builds is the development version `1.1.0-dev.5`: this is a TEST artifact, delete it afterwards, it must never be published.
```bash
SCR=~/aicc-sign-scratch
git -C "$PLUG" worktree add --detach "$SCR" HEAD      # HEAD = the commit with UPDATE_PUBLIC_KEYS committed (A4)
cd "$SCR"
bin/build-release.sh --out ~/aicc-sign-test            # ZIP + .sha256 + manifest.json; prints a loud WARNING if no key is baked
hdiutil attach /Volumes/<STICK-1>/aicc-keys-primary.dmg     # until the USB copy is verified (A3) attach the Mac copy of the vault image instead (its location is in your private key notes)
MAN=~/aicc-sign-test/ai-commerce-copilot-<version>.manifest.json; ZIP=${MAN%.manifest.json}.zip; SIG=${MAN%.json}.sig
AICC_RELEASE_SIGNING_KEY_FILE=/Volumes/AICCKEYS-PRIMARY/aicc-release-primary.key php bin/sign-release.php sign --manifest "$MAN"
hdiutil detach /Volumes/AICCKEYS-PRIMARY
php bin/sign-release.php verify --manifest "$MAN" --sig "$SIG" --zip "$ZIP"              # -> verified: <version> signed <UTC> by key <your primary fingerprint>
```
Expected: `signed <version> with key <your primary fingerprint>`; the `key_id` in the `.sig` equals the fingerprint you wrote down. Now the rejections (each MUST fail with `NOT VERIFIED` or `refusing`):
```bash
python3 - "$MAN" /tmp/m.bad <<'PY'
import json,sys; m=json.load(open(sys.argv[1])); m["version"]="9.9.9"; json.dump(m,open(sys.argv[2],"w"))
PY
php bin/sign-release.php verify --manifest /tmp/m.bad --sig "$SIG" --pubkeys "<primary>,<standby>"   # NOT VERIFIED (bad_signature)
cp "$ZIP" /tmp/z.bad; printf X | dd of=/tmp/z.bad bs=1 seek=200 conv=notrunc 2>/dev/null
php bin/sign-release.php verify --manifest "$MAN" --sig "$SIG" --zip /tmp/z.bad                         # refusing: the ZIP does not match the manifest
```
Also proven in the self-test (run the script to see them all): a flipped signature bit, an altered signing time, an unrelated key, an empty/garbage `.sig`, a world-readable key file (refused), a missing key variable, a ZIP built with no key (refused), and the independent PHP/sodium hand-check from `docs/launch/update-signing.md` section 4 that needs no AICC code. Delete `~/aicc-sign-test` and the scratch worktree afterwards (`cd ~ && git -C "$PLUG" worktree remove --force "$SCR"`; they hold no secret). The publish tool's local checks (`publish-plugin-release.sh`, signature verified against `endpoints.conf`, tampered ZIP and bit-flipped signature refused) were also proven in the sandbox.

Real signing for launch is NOT done here: it happens at `production-promotion.md` step 6.10 after you approve that step.

### A6. What keeps the updater launch-blocked until this is done
* Empty `UPDATE_PUBLIC_KEYS` -> the shipped build bakes no key -> a plugin with no key is never offered updates (fail-closed), `bin/sign-release.php sign` refuses to sign it, and the Control Plane `check-launch-blockers.php` gate rule 5h-1 reports a blocker (5h: no downloadable release at all).
* No `.manifest.sig` next to the release -> `publish-plugin-release.sh --env production` refuses; the host installer re-verifies.

### A7. Recovery and rotation (short; full text: Plugin `docs/launch/update-signing.md` section 5)
* Primary lost or suspected: sign the next release with the STANDBY (every installed store trusts it because both keys are baked), build it baking `standby,<new key>`, wait until the fleet adopted it, destroy the old primary. This is why the standby exists from day one. A stolen primary can still sign until the fleet moved: use the emergency line `define( 'AICC_UPDATE_PUBLIC_KEYS', '<standby>' )` for stores that cannot wait.
* Both lost: ship a new plugin ZIP by hand (account page download); stores then need a manual install. Keep the two secret copies of each key (stick + password manager) in different places and test the standby sign path once a year with the same commands as A5.
* Never more than two keys are honoured. Rotate on a calendar (suggest yearly), not only on suspicion.

## B. Backup encryption key (RSA 4096 certificate)

The repo's tooling (verified in `infra/backup/README-backup.md` section "Encrypted off-host copies" and `pull-offhost.sh`): the Mac pulls the verified backup, encrypts each file with `openssl cms -encrypt -aes-256-cbc` to YOUR certificate (RSA >= 3072 enforced, expiry > 1 day enforced, a file that also contains a private key is refused), stores `<name>.cms` plus sidecars, and deletes the plaintext. The private key must NOT be on the pulling Mac.

### B1. Generate the pair on the encrypted vault (5 min)
Use a third small vault (or reuse STICK-1's vault: it is only a file store; a separate `AICCKEYS-BACKUP` image on STICK-2 is cleaner). Same `hdiutil create ... -volname AICCKEYS-BACKUP` / `attach` as A1, then:
```bash
cd /Volumes/AICCKEYS-BACKUP && umask 077
openssl req -x509 -newkey rsa:4096 -nodes -keyout aicc-backup-recipient.key -out aicc-backup-recipient.crt -subj "/CN=aicc-backup-recipient" -days 3650
chmod 600 aicc-backup-recipient.key
openssl x509 -in aicc-backup-recipient.crt -noout -fingerprint -sha256 -enddate        # write the SHA-256 fingerprint and the expiry date down
```
(`-nodes` = no passphrase on the key file itself; its protection is the encrypted vault plus the password manager. A passphrase-protected key would make `decrypt-offhost.sh` prompt on a terminal: not exercised, so not recommended.) Store `aicc-backup-recipient.key` in the password manager as a secure note too (two copies: vault + password manager). Do NOT copy the `.key` anywhere on the Mac's disk.

### B2. Place ONLY the certificate on the Mac (1 min)
```bash
mkdir -p ~/.config/aicc && install -m 644 /Volumes/AICCKEYS-BACKUP/aicc-backup-recipient.crt ~/.config/aicc/backup-recipient.crt
grep -c PRIVATE ~/.config/aicc/backup-recipient.crt        # must print 0
hdiutil detach /Volumes/AICCKEYS-BACKUP
```
Install it into the LaunchAgent. Today's staging agent (`com.aicc.offhost-pull`) pulls PLAINTEXT staging copies; the production agent is installed at promotion (`production-promotion.md` step "backups + production off-host key/LaunchAgent") with:
```bash
infra/backup/macos/install-launchd.sh --env production --stage-ip <IPV4> --expect-id <32 hex> --encrypt-to $HOME/.config/aicc/backup-recipient.crt --apply
```
(From `cd "$SITE"`.) Optional now (proves the chain before launch day): run the same installer WITHOUT `--apply` (dry run) with `--stage-ip 157.230.110.211 --key ~/.ssh/aicc_cp_stage_offhost --dest ~/aicc-offhost-backups-stage --encrypt-to ...` to see the plist; to switch the staging agent to encrypted pulls, add `--apply` (it replaces the staging agent; reversible with `--uninstall --apply`). Note the pull then writes `.cms` next to the existing plaintext files (see B5).

### B3. Test encrypt / decrypt round trip (10 min, with the real key)
After the first encrypted pull (hourly, or run the runner by hand):
```bash
ls ~/aicc-offhost-backups-*/ | grep '\.cms$' | head                     # ciphertext only for new sets
hdiutil attach /Volumes/<STICK-2>/aicc-keys-backup.dmg
infra/backup/decrypt-offhost.sh --key /Volumes/AICCKEYS-BACKUP/aicc-backup-recipient.key \
   --in ~/aicc-offhost-backups-<env>/aicc_cp-<ts>-<label>.sql.gz.cms --out /tmp/restore-proof.sql.gz         # checks the plaintext sha256 against the sidecar
gzip -dc /tmp/restore-proof.sql.gz | head -5 ; rm -f /tmp/restore-proof.sql.gz ; hdiutil detach /Volumes/AICCKEYS-BACKUP
```
"An unreadable-at-rest copy that has never been decrypted is a hope, not a backup": do this once after the first encrypted pull and once per quarter. Proven in the sandbox (47 checks): new sets stored as `.cms` only (0600 file, 0700 folder, no plaintext, no `.partial`), the customer-data marker not visible in the ciphertext, byte-identical decrypt with OpenSSL 3 AND with LibreSSL (the LaunchAgent's `/usr/bin/openssl`), cross-decrypt both ways, wrong key rejected without leaving output, damaged ciphertext rejected, 2048-bit certificate / certificate-with-key / missing / relative path refused, production pull without `--encrypt-to` refused before any ssh, installer dry-run carries `--encrypt-to` and no key.

### B4. Failure and recovery
| Situation | Effect | What to do |
|---|---|---|
| Private key lost (both copies) | Mac copies unreadable; the host's own hourly sets are unaffected | generate a new pair, point the agent at the new certificate; the old `.cms` stay unreadable (delete them after the host holds good sets) |
| Private key leaked | old Mac copies readable by the leaker | new pair, new certificate, then delete old `.cms` copies |
| Certificate within 24 h of expiry (10-year default; calendar a reminder for year 9) | the pull REFUSES (the host raises `offhost_stale` after 36 h) | generate a new pair (B1) and point the agent at the new certificate; keep the old key for the old ciphertext |
| Rotation | older ciphertext needs the OLD key | keep every retired private key in the vault |
| Mac stolen / Time Machine to cloud | attacker gets ciphertext only | nothing; the key is not on the Mac |

### B5. What happens to the old UNENCRYPTED copies (measured) - ONE rule: T+14 days, after a production decrypt
The pull never encrypts or deletes older plaintext sets by itself; tiered retention keeps them up to 8 weeks (proved in the sandbox). On this Mac `~/aicc-offhost-backups-stage` holds 67 plaintext files (STAGING data from the stage host, written by the plaintext staging agent; no `.cms`; the count changes while the agent runs). Production writes to a new folder `~/aicc-offhost-backups-production`, so no production data ever rests there in plaintext.

**Do NOT delete the staging folder after the first decrypt test, and not "once the host is promoted".** The staging copies are the evidence for the promotion rollback window (production-promotion.md R1/R2). The single rule used in every document: delete them at **T+14 days after the promotion**, and ONLY after a PRODUCTION encrypted set in `~/aicc-offhost-backups-production` has been decrypted successfully (B3 with a `.cms` from that folder) and the rollback window is closed. It is pre-production staging data and must never be restored over production. Cleanup (preview first; proven not to touch `.cms*` files):
```bash
D=~/aicc-offhost-backups-stage      # the plaintext staging folder
find "$D" -maxdepth 1 -type f \( -name 'aicc_cp-*.sql.gz' -o -name 'aicc_cp-*.sql.gz.sha256' -o -name 'aicc-files-*.tar.gz' -o -name 'aicc-files-*.tar.gz.sha256' \) -print     # review the list
find "$D" -maxdepth 1 -type f \( -name 'aicc_cp-*.sql.gz' -o -name 'aicc_cp-*.sql.gz.sha256' -o -name 'aicc-files-*.tar.gz' -o -name 'aicc-files-*.tar.gz.sha256' \) -delete
```
A true shred is impossible on APFS/SSD; FileVault (ON) protects deleted blocks at rest, which is why the real private keys are never written to the internal disk. After the plaintext files are gone, the staging folder itself can be removed wholesale.

### B6. Honest limits
* Encryption is on the Mac, not on the host: the host's own copies stay plaintext on its disk (same trust as the live database); the plaintext exists in a 0600 temp file in the 0700 folder for the seconds between download and encryption.
* The Mac copy is only as available as the Mac (`README-backup.md`: at most ~4.7 h old, 0 failures in 26.5 h measured). A second always-on copy is a separate owner decision (not in this kit).
* The dashboard and `status.json` acks use the PLAINTEXT hash, so `offhost_stale` keeps working with encryption.
