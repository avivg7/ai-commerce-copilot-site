# infra/

Deployment-side material for the AICC staging/production Linux host. Written and tested locally first; since 2026-10-21 it is also **installed and running on the Linux staging host `stage.copilt.org`** (the independent review compared ten installed files byte for byte with the repository and found them identical; evidence in `~/Downloads/AICC-cutover-evidence/linux-stage/`). **Nothing here has been run for PRODUCTION**: there is no production host, no production wp-config/release path and no production Caddy start on Linux (`docs/cutover/runbook.md` sections 10 and 11).

| Directory | What it is |
|---|---|
| `provision/` | Droplet creation package (cloud-init, verifier) and stack installation scripts |
| `systemd/` | Units for the edge, backups, wp-cron, cert-expiry timers, and the failure-status hook read by AICC Ops |
| `php/`, `mysql/`, `fail2ban/`, `logrotate/` | Service configuration for PHP-FPM, MySQL, fail2ban and log rotation |
| `backup/` | Backup, restore-test and off-host pull scripts (writes the `status.json` that AICC Ops reads) |
| `release/` | Release build, deploy and activation scripts |
| `stack-tests/` | Local lint and tests for the infrastructure scripts (`npm run infra:lint`, `npm run infra:test`) |
| **`aicc-ops/`** | **AICC Ops: tiny first-party, operator-only observability (collectors, SQLite history, alerts, capacity verdicts, loopback UI). Python 3.12 stdlib only. Tests: `npm run ops:test`. See `aicc-ops/README.md`.** |
| **`sentinel/`** | **External availability sentinel: design (`DESIGN.md`, failure-mode table, deployment options) and a stdlib reference implementation. Not deployed. Tests: `npm run sentinel:test`.** |

Two observers, deliberately separate: AICC Ops explains *why* from inside the host; the sentinel answers *is it reachable from outside* from a different failure domain; DigitalOcean Monitoring (email/Slack) stays as the independent safety net.

## Stack provisioning: the Linux STAGING host (section owned by the provisioning work)

Target: DigitalOcean Basic Regular, **1 vCPU / 2 GiB RAM / 50 GiB**, Ubuntu 24.04 LTS, 2 GiB swapfile (`vm.swappiness=10`), UFW 22/80/443 tcp, fail2ban, no HTTP/3. Staging `stage.copilt.org`; production `www.copilt.org` later on the same architecture. Stage 1 (cloud-init) is `provision/cloud-init.template.yaml`; everything below is installed afterwards, by reviewed scripts, step by step over SSH. **Nothing in this section has been run on a real Droplet.**

**Bring-up order (details, verification and rollback per step: `provision/RUNBOOK-stage-bringup.md`):** 0 lint+tests, droplet verified, DNS A record -> 1 `push-bundle.sh` -> 2 stage-2 SSH hardening (`stage2-verify-second-session.sh` in a second session, then `harden-stage2.sh`) -> 3 `install-stack.sh` (preflight, identity, packages, users-dirs, caddy, wpcli, php, mysql, sysctl, scripts, systemd, logrotate, fail2ban, services, verify) -> 4 `create-staging-db.sh`, `render-wp-config.sh` -> 5 `install-stack.sh --only edge-env` -> 6 `build-cp-release.sh` + `deploy-release.sh --kind cp --first-install`, `wp core install` -> 7 `build-site-release.sh --target stage` + `deploy-release.sh --kind site` -> 8 Caddyfile (rendered by `scripts/ops/render-edge.mjs --mode stage`), `--only caddyfile`, `--only enable-edge` (Let's Encrypt staging CA first, then the real one) -> 9 `--only enable-timers` -> 10 `operator-tunnel.sh` -> 11 `backup/pull-offhost.sh` -> 12 final checks.

### Memory budget (2048 MiB; the owner chose this size on purpose)

| Component | Typical steady state | Configured worst case | systemd cap (High / Max) | Why this number |
|---|---|---|---|---|
| Kernel, systemd, sshd, journald, chrony, fail2ban, DO agent | ~250 MiB | n/a | n/a | estimate for Ubuntu 24.04 server; confirm with `free -m` on the host |
| MySQL 8.0 | measured 160 MiB idle, 182 MiB after a WordPress install and warm-up; expect 330-400 once the pool fills | pool 192 + 30 connections x ~3 + ~150 = ~430 | 600 M / 720 M | pool 192 MiB (the working set of a small store fits several times; **chunk size set to 64 MiB because 8.0 rounds the pool up to a multiple of 128 MiB: "192M" silently became 256M, found by running a real mysqld**), `performance_schema` OFF (saves tens to hundreds of MiB), `max_connections` 30 (3 PHP workers + cron + backup + restore check + Ops + admin), table caches 800, binlog OFF, socket only |
| PHP-FPM (`aicc` pool) | master ~35 + 3 workers (measured RSS 89-97 MiB each, mostly shared OPcache pages) + OPcache 128 MiB shm | 3 x 192 MiB (`memory_limit`) + 128 + 30 = 734 | 640 M / 900 M | `pm.max_children=3` on one vCPU (the extra workers only overlap MySQL waits), `max_requests=300`, OPcache **128 MiB: measured 68 MiB used by 1,709 scripts after only front-end/REST/store warm-up, wp-admin adds more** |
| Caddy 2.11.x | measured under load: **PSS up to 247 MB, RSS 255-258 MB** (the original 40-80 MiB estimate was wrong; idle is lower) | `GOMEMLIMIT=256MiB` | 320 M / 450 M | static files + TLS + gzip of WordPress responses + page cache charged to the cgroup. `MemoryHigh` must sit ABOVE the measured peak: at 200 M the kernel reclaimed the unit continuously (review M-1) |
| wp-cron (every 2 minutes) | 60-120 MiB for a few seconds; measured 2.3 CPU-s per run | `memory_limit` 192M | Max 256 M | `Nice=10` |
| backup (03:30 UTC) | ~30 MiB (streaming dump + gzip) | | Max 256 M | `Nice=19`, idle IO class |
| Page cache / free | whatever is left (>= 500 MiB) | | | MySQL `O_DIRECT` keeps InnoDB out of the page cache |

Sum of the three `MemoryHigh` values (640 + 600 + 320) 1560 MiB + ~300 MiB OS/cache floor = 1860 MiB < 2048 MiB (AICC Ops `MemoryHigh=48M` and the transient wp-cron / backup runs come on top: 1860 + 48 + ~120 = ~2030 MiB in the worst simultaneous case, which is why nothing more can be added to these three without removing something; the review measured the real peak at 711 MB used of 1,967 MB); the 2 GiB swapfile (swappiness 10) is the safety net, not capacity. `MemoryMax` values (900 + 720 + 450) intentionally exceed RAM: they are per-service ceilings that protect the others (OOM score of mysqld is lowered: PHP workers die first and respawn in milliseconds). `npm run infra:lint` recomputes this arithmetic from the files.

### Local trust boundary of the PHP user (security review M1, 2026-10-21)

Code running as `aicc-cp` (WordPress, WooCommerce, the plugin, WP-CLI cron) used to reach three unauthenticated loopback services: Caddy's admin API `127.0.0.1:12019` (it can `POST /load` a whole new configuration: serve `/var/lib/aicc-edge` TLS keys, drop the wp-admin/wp-login/xmlrpc denies), the operator listener `127.0.0.1:8443` and the AICC Ops UI `127.0.0.1:9190`, plus the cloud metadata service `169.254.169.254`; `wp_remote_get('http://127.0.0.1:12019/config/')` worked because `WP_ACCESSIBLE_HOSTS` contained `localhost,127.0.0.1`. Defence in depth, three layers:

1. **`WP_ACCESSIBLE_HOSTS` is `stage.copilt.org` only** (`provision/wp-config.stage.template.php`; WordPress always lets a request to its own site host through). Nothing in the Control Plane makes any other outbound call on staging.
2. **cgroup IP filter** on `php8.3-fpm.service` (`systemd/overrides/php8.3-fpm.service.d/aicc.conf`) and on `aicc-wp-cron.service`: `IPAddressDeny=127.0.0.0/8 ::1/128 169.254.0.0/16`, `IPAddressAllow=127.0.0.53/32` (the systemd-resolved stub). This holds for raw PHP sockets and `file_get_contents()`, which layer 1 does not cover. It was checked that PHP-FPM and WP-CLI need NO loopback TCP: MySQL is the unix socket (`skip-networking`), Caddy reaches the pool over `/run/php/aicc-cp.sock`, WP-Cron is a timer, Action Scheduler's async runner is off, and the plugin's only outbound call is the entitlement webhook. **Not covered:** an operator running `wp ...` by hand as `aicc-cp` (`sudo -u aicc-cp wp ...`) is outside these units; use `sudo systemd-run --uid=aicc-cp -p IPAddressDeny=127.0.0.0/8 -p IPAddressDeny=::1/128 -p IPAddressAllow=127.0.0.53/32 --wait --pipe ...` for anything that executes untrusted code. **Production:** the Control Plane must reach `api.copilt.org` (the entitlement webhook); that is a public address, not denied here, so no `IPAddressAllow` is needed, but `WP_HTTP_BLOCK_EXTERNAL=true` with `WP_ACCESSIBLE_HOSTS=api.copilt.org` stays mandatory (the production wp-config template in `provision/` records it). Never add `127.0.0.1` or `169.254.169.254` to `IPAddressAllow`.
3. **Sandbox** of the FPM unit in its own drop-in `20-aicc-sandbox.conf` (removable on its own): `NoNewPrivileges`, `PrivateTmp`, `PrivateDevices`, `ProtectHome`, `ProtectSystem=strict` with `ReadWritePaths` for uploads, `/var/lib/aicc-cp`, `/var/log/aicc-cp` and the global FPM log, kernel/cgroup/clock/hostname protection, `RestrictSUIDSGID/Realtime/Namespaces`, `LockPersonality`, native syscall architecture, address families `AF_UNIX AF_INET AF_INET6 AF_NETLINK`, and a minimal capability set for the root master (`SETUID SETGID CHOWN FOWNER DAC_OVERRIDE KILL`; workers hold none). **Deliberately not set:** `MemoryDenyWriteExecute` (PHP's PCRE JIT maps writable+executable memory) and `SystemCallFilter` (an untested filter ends in SIGSYS).

**What was and was not exercised.** `npm run infra:lint` checks the files (keys, paths the installer creates, the required denies, the absence of the two risky directives) with negative tests, and the rendered wp-config. **Not exercised on a running systemd:** the eBPF IP filter, the namespace sandbox and the capability set were NOT run (no PID 1 systemd on the Mac; the Ubuntu container harness needs the Docker daemon). First deploy on the host: `sudo systemctl daemon-reload && sudo systemctl restart php8.3-fpm`; check `curl -sI https://<host>/pricing/`, `journalctl -u php8.3-fpm -n 30`, `sudo -u aicc-cp wp --path=/srv/aicc/cp/current cron event list`, `systemd-analyze security php8.3-fpm`; and prove the filter: `sudo systemd-run --uid=aicc-cp -p IPAddressDeny=127.0.0.0/8 -p IPAddressAllow=127.0.0.53/32 --wait --pipe curl -s -m 3 -o /dev/null -w '%{http_code}' http://127.0.0.1:12019/config/` must print `000`. If the sandbox drop-in breaks the pool, delete `20-aicc-sandbox.conf`, `daemon-reload`, restart.

**Residual risk, said plainly:** the Caddy admin API stays on loopback TCP (AICC Ops reads `/metrics` there), unauthenticated. Layers 1-2 close it for the PHP user; any OTHER local code execution (a compromised `aicc-ops` or `aicc` user, a root process) can still use it. A unix-socket admin endpoint with group permissions for `aicc-ops` only is the stronger fix and needs the Ops caddy collector to speak HTTP over a unix socket (not done here).

### What each guard does (short)

* **Fail closed:** every script has `set -euo pipefail`, refuses non-root where it must run as root, has `--dry-run`, and the stage tooling refuses `139.59.157.231`, `www/api/apex copilt.org`, and the production SSH key by name. The stack installer refuses a host without `/etc/aicc-stage-identity` saying `AICC_ENV=staging`.
* **Releases:** immutable versioned trees, atomic `ln -sfn` + `mv -T` swap, health gate (twice in a row within 30 s) with automatic rollback, Control Plane activation **refused without a successful dump younger than 15 minutes**, code rollback is not a database rollback (additive-migration rules in `release/README.md`).
* **Backups:** daily dump + separate `0600` files archive + restore smoke into `aicc_restore_check`, `status.json` for AICC Ops (`"status":"ok|failed"`, `last_success`), 7-day retention that never deletes the newest three sets, off-host pull to the Mac with 14 copies.
* **fail2ban:** `aicc-wp-login` counts POSTs to `/my-account/` and `/wp-login.php` (rate) and 403/429 on `/wp-login.php`, `/xmlrpc.php`, `/wp-admin/`, `/wp-cron.php`; it **cannot** tell a failed login from a successful one (WordPress answers both with 200/302 and the log has no body); the plugin's own throttle is the real login defence. `caddy-4xx-flood` bans 60 client errors per minute, **not counting 421** (unknown-Host answers from scanners that use the IP as host name: 3,172 in 47 minutes on staging, from many addresses, 0 bans). **Limits (review M-6):** `aicc-wp-login` counts EVERY POST to `/my-account/` and `/wp-login.php`, successful or not, and bans the whole ADDRESS for 1 hour after 10 in 10 minutes, so people behind one NAT share a budget; `ignoreip` is loopback only as shipped. To exempt more addresses create the optional operator-owned `/etc/fail2ban/jail.d/zz-aicc-local.local` (absent by default, never touched by the installer; syntax in `fail2ban/jail.d-aicc-edge.local`). Loopback is never banned (the operator tunnel arrives from 127.0.0.1).
